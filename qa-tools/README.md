# VELORA: проверка перед каждым получателем

`verify-client-readiness.mjs` читает публичный сайт и создаёт доказательства. Он не отправляет сообщения, не нажимает запись/звонок, не меняет админку и не устанавливает браузеры. Страница не может отправить POST/PUT/PATCH/DELETE через обычные HTTP-запросы этого браузерного контекста.

## Запуск

Нужны Node.js 20+ и уже установленные Playwright, Chromium, Firefox, WebKit с системными зависимостями. Версию Playwright закрепляет существующий workflow; локальную установку скрипт не выполняет.

```sh
node qa-tools/verify-client-readiness.mjs client-manifest.json --out qa-results
```

Начальный результат **всегда `ready:false`**. Код выхода `0` означает только завершённую техническую проверку; `2` — FAIL/BLOCKED/UNKNOWN, `1` — некорректный манифест или ошибка самого процесса. Успешный GitHub Actions run не разрешает рассылку.

Манифест описывает **точный опубликованный сайт**, все карточки услуг и точный текст предполагаемого сообщения. Пример формата — `fixture-manifest.json`, это заведомо непригодный для рассылки учебный адрес. `services.selector` должен выбирать каждую карточку, `image_urls` — допустимые итоговые URL её фотографий, `image_alt` — точный alt. Совпадение изображения с услугой по смыслу подтверждает менеджер визуально. `cta_selector` выбирает крупные кнопки, а не любые текстовые ссылки. Значение `44` — наш минимальный размер кнопки, не заявление о полной сертификации доступности.

Для бизнеса без онлайн-записи указать `booking_required:false` и `booking_not_applicable_reason`. Для редиректов явно перечислить `allowed_redirect_urls` сайта и `allowed_booking_redirect_hosts` записи; неожиданный домен не считается успехом.

Проверяются HTTP и конечный URL, декодирование всех `<img>` и CSS-фонов, карточки/alt/URL/заголовки, точные телефон и запись, буквальные запрещённые фразы, переполнение, доступность и перекрытие кнопок. Для lazy-фото страница прокручивается до низа. Затем она возвращается наверх: каждый PNG — **один первый экран**, `fullPage:false`, 390×844 или 1440×900. Внешняя запись проверяется публичным GET; создание настоящей записи не проверяется.

## Устройства и честное покрытие

Всегда запускаются четыре профиля: Chromium 1440×900, Chromium Android 390×844, WebKit iPhone 390×844, Firefox 1440×900. Android/iPhone — явно обозначенные эмуляции, не настоящие устройства. В отчёте сохраняются реальная ОС исполнителя, браузер/версия, viewport, режим и рекламируемый user-agent отдельно.

По умолчанию нужны эмуляции iOS/Android и Chromium/Firefox **на Windows**. Linux не закрывает Windows. Для Windows запустить тот же манифест существующим runner на Windows и передать его JSON-отчёт в `platform_reports`; новый платный сервис не нужен. Если возможности нет, Windows остаётся UNKNOWN и итоговая готовность закрыта. Настоящие iPhone и Android этим harness не проверяются; этого нельзя утверждать клиенту.

## Допуск менеджера

После проверки менеджер смотрит фактические PNG, сайт, фотографии, контакт и точный текст. Отдельный исполнитель проверяет реальное сохранение/перезагрузку/восстановление админки. Затем создаётся `evidence.json`:

```json
{
  "subject_sha256": "ИЗ ОСНОВНОГО QA-ОТЧЁТА",
  "platform_reports": ["windows/qa-fixture-readiness-report.json"],
  "admin_save": {
    "status": "PASS",
    "site_url": "ТОЧНЫЙ URL САЙТА",
    "tested_at": "ФАКТИЧЕСКОЕ ВРЕМЯ ISO",
    "evidence_ref": "Ссылка или путь на реальную проверку",
    "loaded": true,
    "saved": true,
    "persisted_after_reload": true,
    "advanced_fields_preserved": true,
    "public_reload_verified": true,
    "restored": true,
    "before_sha256": "ХЕШ ИСХОДНОГО BRIEF",
    "saved_sha256": "ХЕШ ИЗМЕНЁННОГО BRIEF, ОТЛИЧАЕТСЯ ОТ ИСХОДНОГО",
    "restored_sha256": "СОВПАДАЕТ С before_sha256",
    "verified_public_html_sha256": "html_sha256 ИЗ QA-ОТЧЁТА ПОСЛЕ ВОССТАНОВЛЕНИЯ"
  },
  "manager_approval": {
    "status": "APPROVED",
    "reviewer": "Имя независимого менеджера",
    "reviewed_at": "ФАКТИЧЕСКОЕ ВРЕМЯ ISO",
    "evidence_ref": "Ссылка или путь на заключение менеджера",
    "subject_sha256": "ИЗ ОСНОВНОГО QA-ОТЧЁТА",
    "message_sha256": "outreach_message_sha256 ИЗ QA-ОТЧЁТА",
    "screenshot_sha256": "sha256 ПЕРВОГО ЭКРАНА outbound_profile",
    "content_verified": true,
    "photos_visually_relevant": true,
    "design_checked": true,
    "contact_verified": true,
    "admin_usable": true,
    "ready_for_use": true
  }
}
```

Нельзя проставлять эти поля вместо реальной проверки. Harness проверяет полноту, привязку к снимку и целостность отчёта, но не выдаёт внешнее свидетельство за собственное тестирование админки. Изменённый brief должен действительно отличаться; после возврата исходного состояния сверяются хеши. Токены, пароли и админ-URL с секретом в отчёт не включаются.

```sh
node qa-tools/verify-client-readiness.mjs --finalize qa-results/qa-fixture-readiness-report.json --evidence evidence.json --out qa-final
```

Только итоговый `*-final-readiness.json` может содержать `ready:true`, когда пройдены все проверки и приложены подходящие доказательства. Изменение сайта, фотографий, контакта или текста отменяет старое одобрение. Этот файл не заменяет блокировку исполнителя, проверку истории отправок и лимит кампании.

## Пробелы прежнего отчёта

В `draft-qa/report.json` по Viola и Stcolor подтверждены только ширины 390/1440, отсутствие overflow/битых изображений и телефонные ссылки. `deployed:false`, `admin_tested:false`. Нет доказательств WebKit/Firefox/Windows, фото внутри каждой карточки, точной записи, размеров и перекрытий CTA, первого экрана, живого сохранения админки или допуска менеджера. Старые `pass:true` поэтому не означают готовность к отправке.
